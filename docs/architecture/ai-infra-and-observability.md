# AI infra notes: local serving tradeoffs, and the observability

This grounds the next piece of work (observability and serving-infra hardening, before any web UI work) in the same discipline the rest of this project uses, measure first, don't guess, and it captures a discussion about where this project's choices sit in the wider AI-infra landscape, since that context is worth keeping rather than losing to chat history.

## Local inference serving: where Ollama sits, and what it trades away

Ollama is a thin, developer-friendly wrapper around `llama.cpp`. That lineage explains both why it was the right call for this project and exactly where it would stop being the right call.

**What it optimizes for:** a single machine, a single user, "just works" model management (`ollama pull`, `ollama run`), and GGUF-quantized weights, which is why `qwen2.5-coder:14b` fits in 9GB instead of the ~28GB fp16 would need. That matches this project's actual setup: the model is assumed to be running locally on the same machine as the agent, with the project developed on an M4 MacBook with 24GB of unified memory and one task running at a time. A 16GB machine can still work, but it will be noticeably slower and the benchmark runs will take longer.

**What it doesn't do, and why that's a real boundary, not a hypothetical one:**

- **No continuous batching.** vLLM, TGI, and SGLang all interleave many requests' token generation on the same GPU, so a batch of 50 concurrent users costs barely more wall-clock than one. Ollama serves requests close to sequentially. The plan's own "scaling the eval harness" post-MVP item (running tasks concurrently across multiple browser instances) would hit Ollama as the bottleneck almost immediately if pushed past a handful of concurrent agents, not the browser layer.
- **Limited prefix/KV-cache reuse, which matters for this project's current numbers, not just a hypothetical future.** Every step in the ReAct loop resends the entire growing message history to `/api/chat`. Unless Ollama recognizes and reuses the shared prefix, step 13 of a 15-step checkout task is re-running prefill over everything from steps 1-12 all over again, every single step. SGLang's RadixAttention and vLLM's automatic prefix caching exist specifically to make that free. This is directly what the plan's "shrink the observation payload" and "latency/cost profiling" items are pointing at, and it's cheap to actually go measure (see below) instead of guessing.
- **Quantization is a quality lever, not just a memory knob.** `qwen2.5-coder:14b` is running at whatever quant Ollama defaulted to (almost certainly Q4_K_M). Four-bit quantization measurably degrades structured-output reliability before it degrades fluent prose. It's plausible some fraction of this project's JSON-parsing edge cases (the three distinct malformed-fence shapes found across Milestones 1, 3, and 8) has a quantization contribution on top of the chat-template issue Milestone 1 diagnosed, but that would need `qwen2.5-coder:14b` run at Q8 or fp16 side-by-side to actually attribute rather than assume.

## What real eval/observability infra has that this project doesn't yet

`benchmark/` is already a small, correct instance of the pattern production agent-eval platforms (LangSmith, Braintrust, Arize Phoenix) are built around, not a toy: ground truth checked programmatically rather than LLM-judged, self-report accuracy tracked as its own calibration metric, and `--repeat N` reporting a spread instead of a single point estimate because this suite has genuine run-to-run variance (see [Benchmark trustworthiness](../analysis/benchmark-trustworthiness.md)). The gap is specifically in per-run diagnostic depth: right now a run is scored pass/fail plus a self-report string and a flat wall-clock time, and that's not enough to answer "why" cheaply.

Proposed additions, ordered by cheapest-to-add and most-directly-connected to this project's own already-open questions:

1. **Per-step timing breakdown.** `agent/loop.py`'s trace currently has `wall_clock_seconds` per whole task, nothing per step. Wrapping the `ollama_chat` call and the `execute_tool` call with `time.monotonic()` and logging `{"model_ms": ..., "tool_ms": ...}` per trace entry is a small change that directly answers the plan's own first post-MVP question, "find out where time actually goes before optimizing anything", with a real number instead of a guess. Given the prefix-caching point above, the likely finding is that model inference dominates and grows per step, not Playwright, but that's a hypothesis to check, not an assumption to build on.
2. **A failure taxonomy instead of a bare pass/fail.** A failed run is currently just a self-report string plus a boolean. The plan's own second post-MVP item wants failures categorized: selector drift, hallucinated action, context overflow, premature give-up, timeout, environment flakiness (this last one didn't exist as a category until this project's own `benchmark/health.py` work made it visible). This can be built retroactively over the existing `logs/` directory, by hand first to establish the categories, then as a rule-based pass over the trace shape, so the biggest bucket can be fixed first and the number can be shown moving, which is the actual point of a failure taxonomy rather than a nicety.
3. **Token/cost accounting per step.** Steps and wall-clock time are tracked; prompt size is not. Given the growing-history cost problem above, logging prompt token count per step would show the actual shape of the cost curve, linear or worse, for a long task like the 13-15 step checkout, which is the concrete number that would tell whether context truncation or summarization (already an open question in this project) is worth building at all.
4. **A regression gate sized to the measured noise band, not a guessed threshold.** The suite's spread is now known empirically (roughly 58-92% across the two most recent 3-pass measurements). That means a gate like "pass rate must not drop below 60%" is meaningful; a gate like "must not drop below 65%" would flap on noise alone and teach nobody anything. Set the threshold from the measured baseline's variance, the way real monitoring infra sizes alerts, not from an arbitrary round number.
5. **Formalize tool-call distribution tracking.** This project already did this once by hand for `ask_clarification` (0 calls in 36 runs, then 1 in 3 after a targeted prompt change, checked for false positives by reading every log). That's exactly what tool-call-distribution monitoring looks like in a production agent system: which declared tools actually get used, and which are dead weight in the context window on every single call. Worth making this a standing report over `logs/` rather than a one-off manual check, since it's the kind of thing that should be noticed the next time a tool is added, not rediscovered by hand again.

## Sequencing

This is planned as the next milestone, before any web UI work. `agent/api.py` remains the deliberately-unassigned stub it already is; nothing here requires it. Item 1 (per-step timing) is the cheapest and most directly useful, and should go first, since it's likely to reshape what item 2 (the failure taxonomy) and any future optimization work actually prioritize.
