# Observability, part 4: a regression gate sized to the measured noise band

## What prompted this

The last item in `docs/ai-infra-and-observability.md`'s observability list, and one the plan document was explicit about how to do, not just that to do it: "set the threshold from the measured baseline's variance, the way real monitoring infra sizes alerts, not from an arbitrary round number." This project has the variance measurement to do that with: three `--repeat 3` passes after the `report_done`/`report_blocked` and `ask_clarification` fixes (PR #13) scored 58%, 75%, 92% min/mean/max, already in the README's Agent runtime metrics table. Milestone 7 established, the hard way, that this suite has real run-to-run variance that isn't noise to average away, so any gate built here has to survive that variance rather than fire on it.

## The actual design problem

A gate is only useful if it does two things at once: stay quiet on a run that's merely unlucky, and fire on a run that's genuinely worse. The plan's own illustrative example ("a gate like 'must not drop below 60%' is meaningful; 'must not drop below 65%' would flap on noise alone") points at setting the threshold near the observed floor, but a threshold sitting *at* the floor (58%) doesn't actually solve the problem: this exact suite has already reproduced 58% with no code change at all (Milestone 7's six-run spread touched a low of 2/7 on a since-fixed version, and this measurement's own floor is 58%). A gate at exactly 58% would flap the next time an honest run lands there again, which is the same failure mode the plan is trying to avoid, just moved down slightly.

So `gate_threshold` in `benchmark/regression_gate.py` sets the line strictly below the observed floor: `((floor_percent - 1) // 5) * 5`, rounded to a clean 5-percentage-point step. 58% -> 55%. This also has to hold when a future baseline re-measurement happens to land exactly on a 5-point line (60%, 80%): the `- 1` before rounding down guarantees the threshold is always at least one point below the floor, never equal to it, which a naive "round down to the nearest 5" would get wrong exactly on those inputs (60% would round down to 60% itself, giving zero headroom). Tested directly in `tests/test_regression_gate.py`.

The other real decision was what to gate *on*. A single fresh run's pass rate is exactly the kind of single-run conclusion this project has already learned not to trust (Milestone 7's whole reason for `--repeat` existing). So `check_regression` takes the **mean** of a fresh multi-pass measurement, the same statistic the baseline itself was built from, and `--repeat` below 2 is rejected outright by the CLI rather than silently gating on one number.

## What this establishes

- `benchmark/baseline.json` holds the measured baseline (min/mean/max pass rate, run count, source, measurement date) as data, not a magic number buried in code, so it can be replaced after a real re-measurement without touching the gate logic itself.
- `benchmark/regression_gate.py` runs the suite via the existing `run_suite_repeated`, computes the mean via a new `per_run_pass_rates` helper (extracted out of `benchmark/runner.py`'s `summarise`, which now calls the same function rather than duplicating the scored/passed logic), and exits non-zero with a `GATE FAIL: ...` message on a real regression, printing the baseline and the actual numbers either way.
- **Deliberately not wired into `.github/workflows/ci.yml`.** Every job already in that workflow (lint, typecheck, test, security, docker-build) runs against static code with no live model or browser dependency, which is exactly why they can run on a GitHub-hosted runner unattended. This gate needs a local `qwen2.5-coder:14b` via Ollama and a real browser session against live sites, the same reason `runner.py`/`report.py` were already documented in `docs/how-to-run.md` as local, manual commands rather than CI steps. The gate belongs in that same local workflow: run it after a change expected to move the pass rate, before merging.
- This closes out the observability milestone `docs/ai-infra-and-observability.md` opened: per-step timing (part 1), a failure taxonomy (part 2), token/cost accounting (part 3), and now this. All four were measured first, not designed from the plan's suggested categories or a guessed number.
